# AI Engineer Portfolio - The Truth Filtering Engine

## 1. 프로젝트 개요

The Truth Filtering Engine은 음식점/카페 블로그 리뷰의 광고성 가능성을 NLP 모델로 추정하고, 그 결과를 지도 기반 서비스에 연결한 프로젝트입니다. AI 기능의 핵심은 리뷰 제목과 본문을 입력받아 광고 가능성 점수를 계산하는 이진 텍스트 분류입니다.

이 프로젝트는 모델 실험 자체보다, 모델 결과를 실제 사용자 흐름 안에서 수집, 전처리, 추론, 저장, 화면 표시까지 연결한 점이 중요합니다.

| 항목 | 내용 |
| --- | --- |
| AI 기능 | 네이버 블로그 리뷰 광고성 가능성 분류 |
| 입력 데이터 | 리뷰 제목, 리뷰 요약 본문, 매장명 |
| 출력 데이터 | 광고 가능성 점수, 광고성/의심/진성 리뷰 구분 |
| 서비스 적용 | FastAPI 추론 API, Supabase 캐싱, React/Flutter 상세 리뷰 화면 |
| 주요 기술 | Python, PyTorch, HuggingFace Transformers, ELECTRA 계열 모델, FastAPI |
| 최종 실험 요약 | PyTorch FP32 기준 AUC 0.8397, F1 0.7788 |

> 기여 기준: 최현석(choihyunseok)의 직접 기여는 모델 연구 자체보다 AI 분석 결과를 웹/앱 상세 화면, 추천, 사용량/캐시 흐름과 연결하는 서비스 적용 영역에 더 가깝습니다.

## 2. 문제 정의

맛집 탐색에서 블로그 리뷰는 유용하지만 광고성 글과 실제 방문 후기가 섞여 있습니다. 단순 키워드 규칙만으로는 다음 문제를 해결하기 어렵습니다.

- "정말 맛있어요", "강력 추천" 같은 표현은 실제 후기와 광고성 리뷰 모두에 등장합니다.
- 협찬/광고 문구가 직접 드러나지 않는 자연스러운 홍보 글도 존재합니다.
- 특정 매장명이나 브랜드명이 반복되면 모델이 내용이 아니라 상호명에 반응할 수 있습니다.
- 사용자는 리뷰 하나하나를 직접 열어 광고 여부를 판단해야 하므로 탐색 시간이 길어집니다.

따라서 리뷰 문맥을 반영하는 NLP 모델을 사용해 각 리뷰의 광고성 가능성을 점수화하고, 서비스 화면에서 낮은 광고 가능성 리뷰를 먼저 확인할 수 있게 하는 것을 목표로 했습니다.

레포에는 학습 데이터셋 전체가 포함되어 있지 않지만, README와 서비스 코드 기준으로 데이터 구성은 다음과 같이 정리할 수 있습니다.

| 구분 | 내용 |

| 입력 필드 | 리뷰 제목, 리뷰 description, 매장명 |
| 라벨 | 광고성 리뷰 여부를 나타내는 이진 라벨 |

## 4. 전처리

서비스 추론 전처리는 `backend/services/preprocess.py`에 구현되어 있습니다.

```text
리뷰 제목 + 리뷰 본문 + 매장명
  -> HTML 태그 제거
  -> HTML entity 디코딩
  -> 불필요한 공백/해시태그/말줄임 정리
  -> 매장명과 브랜드명 마스킹
  -> 제목 [SEP] 본문 형태로 결합
  -> Transformer tokenizer 입력
```

### 전처리 의도

- HTML 태그와 엔티티를 제거해 모델 입력 노이즈를 줄였습니다.
- 상호명과 브랜드명을 일반 표현으로 치환해 특정 매장명에 대한 편향을 완화했습니다.
- 제목과 본문을 `[SEP]`로 결합해 짧은 제목과 본문 preview를 함께 활용했습니다.
- 과도한 규칙 기반 형태소 분석보다 Transformer tokenizer가 문맥을 학습하도록 입력을 정리하는 데 집중했습니다.

## 5. 모델 및 추론 파이프라인

서비스 코드는 HuggingFace Transformers 기반 sequence classification 모델을 사용합니다. 현재 추론 서비스는 `backend/models/GPU/model.safetensors`에 위치한 모델 파일을 로드하도록 구성되어 있습니다.

```text
Naver Blog Review
  -> preprocess(title, description, store_name)
  -> AutoTokenizer
  -> AutoModelForSequenceClassification
  -> Softmax
  -> class 1 probability
  -> is_ad_finetuned_pred 저장
```

### 추론 구현

| 함수 | 역할 |
| --- | --- |
| `load_model()` | 서버 시작 시 tokenizer와 sequence classification 모델을 한 번 로드합니다. |
| `score_is_ad()` | 단일 리뷰 텍스트의 광고 가능성 점수를 계산합니다. |
| `predict_is_ad()` | 광고 가능성 점수를 threshold 기준으로 등급화합니다. |
| `predict_and_score_batch()` | 여러 리뷰를 배치로 추론하고 예측값과 점수를 반환합니다. |

모델 파일이 없거나 로드에 실패한 경우 서버 전체를 중단하지 않고 모델 사용 불가 상태로 전환합니다. 서비스 요청에서는 점수 `0.0` fallback을 사용해 지도 탐색 기능이 완전히 멈추지 않도록 했습니다.

## 6. 모델 선택 이유

리뷰 광고성 분류는 한국어 구어체, 홍보 문구, 음식점명, 짧은 문장 등이 섞인 텍스트 분류 문제입니다. 이 때문에 문맥을 반영할 수 있는 Transformer 기반 한국어 언어모델이 적합했습니다.

ELECTRA 계열 모델은 BERT 계열과 유사하게 문맥 표현을 활용하면서도 비교적 효율적인 분류 모델로 서비스 추론에 연결하기 좋습니다. 프로젝트에서는 최종적으로 ELECTRA 기반 분류 모델을 FastAPI 서버에 연결해 광고 가능성 점수를 산출했습니다.

다만 현재 레포만으로는 전체 학습 코드와 데이터셋을 재현할 수 없으므로, 포트폴리오에서는 "모델 연구 전체를 완성했다"보다 "NLP 분류 모델을 서비스 추론 파이프라인에 연결했다"는 점을 중심으로 설명하는 것이 정확합니다.

README에 정리된 실험 기록 기준으로 모델 개선 과정은 다음과 같습니다.

| 항목 | 내용 |

| 초기 검증 성능 | 기존 검증 데이터에서 AUC 약 0.95, F1 0.9693 수준 |
| 신규 테스트 문제 | 신규 테스트 데이터에서 AUC 0.58까지 하락 |
| 원인 가설 | 특정 가게/표현에 대한 데이터 편중과 상호명 편향 |
| 데이터 개선 | 가게 수 34개에서 122개, 데이터 수 1,360개에서 2,142개로 확대 |

| 최종 결과 | PyTorch FP32 AUC 0.8397, F1 0.7788 |

## 8. 평가 지표

광고성 리뷰 탐지는 단순 Accuracy만으로 평가하기 어렵습니다. 일반 리뷰가 많으면 모두 일반으로 예측해도 정확도가 높게 보일 수 있기 때문입니다.

| 지표 | 사용 이유 |
| --- | --- |
| AUC | threshold에 덜 의존하는 전체 분류력 확인 |
| F1 | 광고성/비광고성 판단의 precision과 recall 균형 확인 |
| Precision | 광고성으로 판단한 리뷰의 신뢰도 확인 |
| Recall | 실제 광고성 리뷰를 얼마나 놓치지 않는지 확인 |

서비스 화면에서는 모델 점수를 이진 라벨 하나로만 보여주기보다 광고 가능성 점수와 등급으로 활용합니다. 이를 통해 사용자가 리뷰를 완전히 배제하기보다 참고 신호로 사용할 수 있게 했습니다.

## 9. 에러 분석

### 1) 상호명 편향

특정 매장명이나 브랜드명이 학습 데이터에서 광고성 라벨과 함께 자주 등장하면 모델이 리뷰 내용보다 상호명에 반응할 수 있습니다. 이를 줄이기 위해 `preprocess.py`에서 매장명과 브랜드명을 마스킹했습니다.

### 2) 과도하게 긍정적인 실제 후기

실제 방문자가 매우 만족해서 쓴 리뷰도 홍보성 표현과 비슷할 수 있습니다. 이런 리뷰는 false positive가 될 가능성이 있습니다. 서비스에서는 광고 가능성이 높다는 결과를 절대 판단이 아니라 참고 점수로 보여주는 방향이 적절합니다.

### 3) 자연스러운 광고성 리뷰

협찬 문구가 직접적으로 드러나지 않는 리뷰는 false negative가 될 수 있습니다. 이 경우 텍스트만으로는 한계가 있으므로 작성 패턴, 링크, 블로그 계정 특성 같은 추가 feature를 고려할 수 있습니다.

### 4) 검색 결과 오매칭

Naver Blog API 검색 결과에는 같은 이름의 다른 지점이나 무관한 글이 섞일 수 있습니다. 백엔드에서 매장명 포함 여부와 주소/카테고리 기반 검색어를 사용해 관련 없는 리뷰를 줄였습니다.

## 10. 서비스 적용

AI 모델은 FastAPI 백엔드의 리뷰 분석 API에 연결되어 있습니다.

```text
사용자 매장 선택
  -> 백엔드가 Supabase 캐시 조회
  -> 부족한 경우 Naver Blog API로 리뷰 수집
  -> 리뷰 제목/본문 전처리
  -> ELECTRA 모델 배치 추론
  -> 광고 가능성 점수 저장
  -> 웹/앱 상세 화면에 리뷰 목록과 점수 표시
```

### 서비스에서 AI 결과를 쓰는 방식

- 상세 리뷰 화면에서 리뷰별 광고성 가능성을 보여줍니다.
- 리뷰 정렬에서 광고 가능성이 낮은 리뷰를 우선 확인할 수 있게 합니다.
- AI 추천 API는 `is_ad_finetuned_pred`가 낮은 리뷰를 기준으로 매장을 추천합니다.
- Supabase에 점수를 저장해 동일 리뷰를 반복 추론하지 않도록 합니다.
- SSE 스트림으로 분석된 배치를 즉시 화면에 반영합니다.

## 12. 트러블슈팅

### 문제 1. 검증 성능과 신규 데이터 성능의 차이

초기 검증 데이터에서는 AUC와 F1이 높았지만 신규 테스트 데이터에서 AUC가 0.58까지 떨어졌습니다.

원인은 데이터가 특정 가게와 표현에 치우쳐 모델이 광고성 문맥보다 상호명/패턴에 과적합했을 가능성이었습니다. 이를 해결하기 위해 가게 수와 데이터 수를 늘리고, 매장명/브랜드명 마스킹 전처리를 추가했습니다.

### 문제 2. 모델 추론 시간이 사용자 경험을 방해함

리뷰를 모두 분석한 뒤 응답하면 사용자는 빈 화면에서 오래 기다려야 했습니다.

FastAPI의 `/api/search/stream`에서 배치 단위로 추론하고 SSE로 중간 결과를 전송하도록 바꿨습니다. 프론트엔드는 분석이 끝나기 전에도 일부 리뷰를 먼저 표시할 수 있게 되었습니다.

### 문제 3. 모델 파일 부재 시 서버 기능 전체가 깨질 위험

개발 환경마다 모델 파일이 없을 수 있고, 모델 로드 실패가 서버 시작 실패로 이어질 수 있었습니다.

`electra_service.py`에서 모델 파일 존재 여부를 확인하고, 로드 실패 시 모델 사용 불가 상태로 두었습니다. 추론 요청에서는 fallback 점수를 사용해 최소한의 탐색 기능을 유지하도록 했습니다.

### 문제 4. 검색 API 결과와 실제 매장 불일치

같은 이름의 다른 지점 리뷰가 섞이면 모델 점수가 정확해도 서비스 결과가 틀릴 수 있습니다.

Naver 검색어 생성 단계에서 매장명, 주소 토큰, 카테고리를 함께 활용하고, 매장명 매칭 필터를 적용해 리뷰 후보 품질을 높였습니다.

| 모델 판단 근거를 사용자에게 설명하지 못함 | 중요 키워드 하이라이트, attention/feature 기반 설명, 근거 문장 표시를 추가합니다. |

| 운영 중 성능 모니터링이 부족함 | 사용자 피드백 기반 오탐/미탐 수집과 주기적 재학습 루프를 만듭니다. |
| threshold 정책이 고정적임 | 서비스 목표에 따라 precision 우선/recall 우선 threshold를 실험합니다. |
| fallback 점수 `0.0`이 실제 점수와 혼동될 수 있음 | 모델 사용 불가 상태를 별도 필드로 내려 UI에서 구분합니다. |
