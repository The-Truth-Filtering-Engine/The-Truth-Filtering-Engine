## 4. 문제 정의

### 4.1 핵심 문제
> **맛집 하나를 고르기까지 평균 15–20분이 소모되는 구조**

사용자 의사결정 흐름과 페인포인트:

| 단계 | 행동 | 페인포인트 |
|------|------|-----------|
| 검색 | "수원 파스타 맛집" 검색 | - |
| 리뷰 탐색 | 5–10개 블로그 리뷰 탐색 | - |
| 리뷰 읽기 | 블로그 리뷰 사진·본문 읽기 | "광고 여부 불명확" |
| 재검색 | 광고 의심으로 재검색 | "재검색 반복 발생" |
| 결정 or 포기 | 불확실한 상태로 맛집 선택 | "배신감 반복 경험" |

### 4.2 기존 서비스 한계

| 한계 | 세부 내용 |
|------|-----------|
| 대가성 고지 은폐 | • 협찬 표시를 본문 최하단에 배치<br>• 모바일에서 스크롤 없이 확인 불가<br>• 사용자 84%가 '끝까지 읽지 않는다' 응답 |
| 신뢰도 판단 기능 미비 | • 네이버는 작성자가 직접 내돈내산 인증을 해야 신뢰도 판단 가능, 그러나 인증 사례가 매우 적음<br>• 카카오맵은 최신순·유용한 순 정렬만 존재 |
| 반복 홍보 문구 오염 | • '찐맛집', '솔직 후기' 등으로 홍보 → 진짜 후기와 홍보 문구 구별 불가<br>• '강추', '인생 맛집' 등 과장 표현<br>• 전체 리뷰 풀의 신뢰도 하락 |

### 4.3 근거 데이터
> "정보는 넘치지만, 신뢰할 수 있는 정보는 부족하다."

- 소비자 10명 중 약 6명(**61.7%**)은 리뷰를 보고 실패한 경험이 있다고 응답
- 리뷰가 너무 많은 제품은 오히려 의심된다는 응답도 **35.2%**
- 공정거래위원회 2024년 SNS 모니터링 결과, 총 **22,011건**의 뒷광고 의심 게시물 발견
  - 플랫폼별: 인스타그램 10,195건 / 네이버 블로그 9,423건 / 유튜브 1,409건

|----------|------|
| 백엔드 서버 | FastAPI (localhost:8000) |
| 외부 노출 | Cloudflare Quick Tunnel (cloudflared tunnel --url) |
| 프론트엔드 | 웹(Vercel), 앱(Flutter) |
| DNS | Cloudflare DNS |

- 로컬 환경에서 실행 중인 FastAPI 서버를 Cloudflare Quick Tunnel로 외부에 노출하여 별도의 클라우드 서버 없이 배포 환경을 구성
- Cloudflare DNS로 도메인을 연결해 웹/앱 클라이언트가 동일한 엔드포인트로 접근

### 7.2 AI 분석 응답 지연

**기존 방식의 한계 (최대 20초 소요):**
1. 클라이언트 요청
2. 리뷰 300개 수집 (Naver API)
3. 모델 추론
4. JSON 응답 반환
→ 여기까지 사용자는 로딩 화면

**SSE 스트리밍 계획:**
1. 클라이언트 요청
2. 리뷰 100개 수집 (Naver API)
3. 1차 batch 모델 추론 → 1차 결과 전송
4. 2차 batch 모델 추론 → 2차 결과 전송
5. 3차 batch 모델 추론 → 3차 결과 전송
6. done: true 전송

**SSE 스트리밍 한계점:**
- Cloudflare Quick Tunnel의 버퍼링으로 인해 연결 종료 후 일괄 전송됨 (실시간 스트리밍 안 됨)

**향후 개선 방향:**
- Cloudflare Quick Tunnel은 공식적으로 SSE 미지원
- → 정식 Cloudflare Tunnel 계정 등록 또는 Cloudflare Workers 도입으로 SSE 스트리밍 안정화

### 7.3 지역 필터 정확도

**문제 상황:**
- AI 추천 기능에서 "현재 위치 주변 음식점"을 추천할 때, 리뷰 데이터의 주소 정보가 불완전하거나 행정구역 표기가 달라서 지역 필터가 누락되는 문제

**지역 필터 누락 예시:**

| 실제 주소 | 리뷰에 저장된 주소 | 매칭 결과 |
|-----------|-------------------|-----------|
| 경기도 수원시 영통구 | 수원 영통 | 불일치 |
| 서울특별시 마포구 | 서울 마포구 | 불일치 |
| 부산광역시 해운대구 | 해운대 | 불일치 |
| 경기도 성남시 분당구 | 성남시 분당구 | 일치 |

**해결 방법:**
- Kakao coord2region으로 현재 행정구역 조회: 사용자의 현재 GPS 좌표를 Kakao API에 넘겨 정확한 행정구역 문자열 호출
- 행정구역 변형 처리: 받아온 행정구역 문자열을 여러 축약형으로 변형
  - "경기도 수원시 영통구" (원본)
  - "수원시 영통구" (도 제거)
  - "수원 영통구" (시 축약)
  - "수원 영통" (구 제거)
  - "영통구" (구만)
  - "영통" (축약형)

### 7.4 분석 사용량 관리

**문제점 / 해결 목표:**

| 문제점 | 해결 목표 |
|--------|-----------|
| 사용량 무제한 → 서버 비용 증가 | 사용자별 분석 사용량 관리 |
| 동일 요청 반복 시 중복 차감 가능 | 중복 과금 방지 |
| 동시 요청 발생 시 데이터 정합성 문제 | 동시성 안전성 확보 |

**분석 사용량 차감 로직 (우선순위):**

| 우선순위 | 조건 | 처리 |
|----------|------|------|
| 1 | freecount > 0 | 무료 횟수 차감 |
| 2 | premiumcount > 0 | 프리미엄 횟수 차감 |
| 3 | coin ≥ 100 | 코인 100 차감 |
| 4 | 모두 부족 | HTTP 402 반환 |

- 동일 store_id 2일 이내 재분석 시 차감 제외

**동시 요청 안전성 확보:**
- 연속 클릭 문제 → Optimistic Concurrency 적용 (현재 값이 일치할 때만 update)
- 현재 값 매칭 조건 기반의 Optimistic Concurrency를 적용해 동시 요청 시 중복 차감 방지

### 7.5 백엔드 향후 개선 방향

| 영역 | 문제 | 개선 방향 |
|------|------|-----------|
| SSE 스트리밍 | Cloudflare 버퍼링으로 SSE 스트리밍 제한 | 정식 클라우드 서버 배포로 전환, SSE 스트리밍 정상화 |
| 배포 안정성 | 로컬 서버 기반으로 운영 불안정 | AWS / GCP 등 클라우드 서버로 이전, 안정적 운영 환경 구축 |
| 코드 품질 | 여러 곳에서 Supabase를 직접 호출 | repository 계층 강화 + typed schema 도입 |
| 테스트 | 자동화 테스트 부재 | SSE format, 사용량 차감 자동 검증 test suite 추가 |
