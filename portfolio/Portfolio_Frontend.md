# Frontend Portfolio - The Truth Filtering Engine

## 1. 프로젝트 개요

The Truth Filtering Engine은 사용자가 지도에서 음식점과 카페를 탐색하면서 네이버 블로그 리뷰의 광고성 가능성을 함께 확인할 수 있는 서비스입니다. 프론트엔드는 사용자의 지도 탐색 흐름을 유지하면서 리뷰 분석 결과, 북마크, 최근 분석, AI 추천을 한 화면 안에서 자연스럽게 사용할 수 있도록 구성했습니다.

이 프로젝트에는 React 웹 클라이언트와 Flutter 앱이 함께 존재합니다. React 웹은 Vite 기반으로 구현되어 Vercel 배포에 맞춰져 있고, Flutter 앱은 모바일/웹 크로스 플랫폼 화면으로 지도 탐색과 상세 분석 경험을 제공합니다.

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | The Truth Filtering Engine |
| 담당 영역 | React 웹 UI, Flutter 인증/설정·앱 화면 흐름, 지도 UX, API/Supabase 연동, SEO/포트폴리오 연동, 디자인 시스템 적용 |
| 사용자 | 음식점/카페를 검색하면서 광고성 리뷰를 걸러 보고 싶은 사용자 |
| 핵심 기능 | 지도 탐색, 장소 검색, 리뷰 상세 분석, 북마크, 최근 분석, AI 추천, 계정 설정 |
| 주요 기술 | React, TypeScript, Vite, Flutter, Riverpod, Kakao Maps, Supabase Auth, CSS Design System |

## 2. 사용자 문제와 화면 목표

일반적인 맛집 탐색 과정에서는 사용자가 지도에서 매장을 찾은 뒤 블로그 리뷰를 여러 개 열어 광고성 여부를 직접 판단해야 합니다. 이 과정은 시간이 오래 걸리고, 사용자는 실제 후기와 홍보성 글을 구분하기 어렵습니다.

프론트엔드의 목표는 다음과 같았습니다.

- 지도 탐색 흐름을 깨지 않고 매장을 선택할 수 있게 합니다.
- 매장 상세 화면에서 광고 가능성이 낮은 리뷰를 우선 확인할 수 있게 합니다.
- 분석 중인 상태를 명확히 보여주고, 결과가 도착하는 즉시 화면에 반영합니다.
- 북마크와 최근 분석을 통해 사용자가 다시 확인할 매장을 쉽게 찾게 합니다.
- 웹과 앱 모두에서 비슷한 정보 구조와 행동 흐름을 제공합니다.

## 4. 사용자 플로우

```text
로그인 또는 테스트 계정 진입
  -> 지도에서 현재 위치/검색어 기준 음식점 탐색
  -> 매장 선택
  -> 기본 정보 확인
  -> 상세 분석 요청
  -> 캐시 결과 또는 SSE 분석 결과 표시
  -> 리뷰 정렬, 원문 열기, 하트/신고 액션
  -> 북마크 또는 최근분석에서 재방문
```

웹에서는 좌측 패널과 우측 지도를 분리해 사용자가 장소를 바꿔도 분석/목록 UI가 안정적으로 유지되도록 했습니다. Flutter 앱은 하단 탭과 bottom sheet 중심으로 모바일 탐색 흐름에 맞췄습니다.

## 5. 컴포넌트 구조

React 웹은 `App.tsx`가 전체 화면 흐름을 조율하고, API/상태/패널을 분리했습니다.

```text
web/src/
├── App.tsx
├── api/
│   ├── places.ts
│   ├── reviews.ts
│   └── user.ts
├── hooks/
│   ├── useAuth.ts
│   ├── useBookmarks.ts
│   ├── useDetail.ts
│   ├── useMap.ts
│   └── useReviewActivity.ts
├── components/
│   ├── RestaurantThumb.tsx
│   └── panels/
└── design-system/
```

| 영역 | 설계 의도 |
| --- | --- |
| `api/*` | fetch, SSE 파싱, 응답 정규화를 화면 코드에서 분리합니다. |
| `hooks/*` | 인증, 지도, 상세 분석, 북마크, 리뷰 활동 상태를 기능 단위로 관리합니다. |
| `components/panels/*` | 지도 옆에서 열리는 사용자 작업 단위를 패널 컴포넌트로 분리합니다. |
| `design-system/*` | 버튼, 아이콘 버튼, 필드, 카드, 뱃지, 토스트, 다이얼로그의 공통 스타일을 제공합니다. |
| `lib/*` | Kakao Map loader, 포맷팅, 사용량 계산, 음식점 모델 변환을 담당합니다. |

Flutter 앱도 `core`, `data`, `features`로 나눠 설정/디자인 시스템/데이터 접근/기능 화면을 분리했습니다.

## 6. 상태 관리

### React 웹 상태

웹은 별도 전역 상태 라이브러리 없이 React hook 중심으로 상태를 나눴습니다.

| Hook | 관리 상태 |
| --- | --- |
| `useAuth` | Supabase session, 테스트 계정 로그인, 인증 헤더 |
| `useMap` | Kakao 지도 인스턴스, 현재 위치, 지도 로딩 상태, 마커, 주변 장소 |
| `useDetail` | 상세 분석 상태, SSE 요청 abort, 리뷰 정렬/페이지, 숨긴 리뷰, 추가 로딩 |
| `useBookmarks` | 북마크 목록, optimistic toggle, 원격 동기화 |
| `useReviewActivity` | 리뷰 하트, 신고, 최근 연 리뷰, 하트한 리뷰 목록 |

`App.tsx`는 현재 활성 패널, 선택 매장, 검색 결과, 사용자 프로필, 최근 분석, AI 추천 상태를 연결합니다. 지도와 패널의 관심사를 hook으로 분리해 하나의 컴포넌트에 모든 비동기 로직이 몰리지 않도록 했습니다.

### Flutter 상태

Flutter는 Riverpod provider를 사용해 현재 사용자, 사용자 프로필, 지도 상태, 북마크, 최근 방문, AI 추천, 리뷰 반응 상태를 관리합니다. 디자인 시스템은 `core/design_system`에 모아 웹과 유사한 버튼/카드/뱃지 톤을 맞췄습니다.

## 7. API 연동

프론트엔드는 백엔드 API 호출을 `web/src/api`로 분리했습니다.

| 파일 | 역할 |
| --- | --- |
| `places.ts` | `/places/nearby-restaurants`, `/places/search-restaurants` 호출과 음식점 payload 파싱 |
| `reviews.ts` | `/api/search/cached`, `/api/search`, `/api/search/stream` 호출, SSE 파서, 리뷰 등급 계산 |
| `user.ts` | `/api/user/me`, 북마크, 최근분석, 코인/프리미엄 API 호출 |

상세 분석은 다음 순서로 동작합니다.

```text
1. 캐시 조회 요청
2. 캐시가 있으면 즉시 상세 화면 렌더링
3. 캐시가 없거나 새로고침이면 SSE 스트림 요청
4. 배치가 도착할 때마다 리뷰 목록 병합
5. 마지막 응답에서 사용량 정보를 사용자 프로필에 반영
```

SSE는 `ReadableStream`을 직접 읽고 `data:` 이벤트를 누적 파싱하는 방식으로 처리했습니다. 요청이 겹칠 경우 `AbortController`와 request id를 사용해 오래된 응답이 최신 화면을 덮어쓰지 않도록 했습니다.

## 9. 핵심 구현

### 1) 지도와 분석 패널을 분리한 화면 구조

지도는 장소 탐색의 중심이고, 좌측 패널은 검색/상세/북마크/최근/추천을 전환하는 작업 영역입니다. 이 구조를 통해 사용자는 지도 맥락을 유지한 채 매장 정보를 비교할 수 있습니다.

### 2) 상세 분석 스트리밍 렌더링

리뷰 분석은 시간이 걸릴 수 있으므로 모든 결과를 기다리지 않고 SSE 배치를 받을 때마다 목록을 갱신합니다. 사용자는 분석이 진행 중이라는 사실과 중간 결과를 동시에 확인할 수 있습니다.

### 3) 북마크와 최근분석 재진입

북마크한 매장이나 최근 분석 항목을 누르면 지도 중심을 해당 매장으로 이동시키고 관련 패널을 열도록 했습니다. 저장 기능이 단순 목록이 아니라 지도 탐색 재진입 경로가 되도록 구성했습니다.

### 4) 사용량 기반 CTA

`detailUsage.ts`에서 무료 분석 기간, 무료 횟수, 프리미엄 횟수, 코인을 기준으로 버튼 라벨과 사용 가능 여부를 계산합니다. 화면은 복잡한 과금 조건을 직접 알 필요 없이 계산된 결과만 렌더링합니다.

### 5) 웹/앱 디자인 시스템 정리

`design-tokens/tokens.json`을 기준으로 웹 CSS token과 Flutter design system을 관리합니다. 버튼, 카드, 배지, 입력 필드, 토스트 등 반복 UI를 공통 규칙으로 맞춰 제품의 일관성을 높였습니다.

## 10. 접근성과 사용성

- 주요 패널에 `aria-label`을 지정해 영역 의미를 명확히 했습니다.
- 버튼과 리스트 아이템은 키보드 포커스 스타일을 유지했습니다.
- 검색/상세/추천 화면에 로딩, 오류, 빈 상태를 각각 분리했습니다.
- 원문 블로그 링크는 새 창으로 열어 사용자가 현재 탐색 흐름을 잃지 않게 했습니다.
- 지도 마커와 현재 위치 오버레이를 시각적으로 구분했습니다.

## 11. 트러블슈팅

### 문제 1. 지도 idle 이벤트로 API가 과도하게 호출됨

지도 이동/확대 중 `idle` 이벤트가 자주 발생하면서 주변 장소 API 호출이 과도하게 발생할 수 있었습니다.

`useMap`에서 지도 상태와 검색 모드를 분리하고, 검색/북마크 포커스 중에는 viewport 자동 검색이 끼어들지 않도록 제어했습니다. 이를 통해 사용자가 선택한 결과가 지도 이동 이벤트에 의해 불필요하게 덮이는 문제를 줄였습니다.

### 문제 2. 상세 분석 요청이 겹칠 때 이전 응답이 최신 화면을 덮음

사용자가 다른 매장을 빠르게 선택하면 이전 스트림 응답이 늦게 도착해 현재 상세 화면을 오염시킬 수 있었습니다.

`AbortController`로 이전 요청을 중단하고, `detailRequestIdRef`로 최신 요청 여부를 검사해 오래된 응답을 무시하도록 처리했습니다.

### 문제 3. 캐시 결과와 스트리밍 결과 병합 시 중복 리뷰 발생

캐시된 리뷰와 새로 수집된 리뷰가 같은 URL을 가질 수 있었습니다.

리뷰 병합 단계에서 URL/ID 기준으로 중복을 제거하고, 정렬과 페이지네이션은 병합된 목록 기준으로 다시 계산했습니다.

### 문제 4. 웹과 앱의 기능 정합성 유지

Flutter 앱에서 먼저 구현된 북마크, 최근분석, 리뷰 하트, 신고 흐름을 React 웹에서도 비슷하게 제공해야 했습니다.

공통 API 응답 모델을 기준으로 웹 타입과 Flutter 모델을 각각 정리하고, 기능별 hook/provider로 상태를 분리해 플랫폼별 UI만 다르게 가져가도록 했습니다.

```bash
npm run build
```

`vercel.json`은 `web` 폴더에서 설치와 빌드를 수행하고 `web/dist`를 배포 산출물로 사용합니다. 환경변수는 `VITE_BACKEND_BASE_URL`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` 형태로 분리되어 있습니다.

Flutter 앱은 플랫폼별 runner가 포함되어 있어 Android, iOS, web, desktop 타깃으로 확장 가능한 구조입니다. 현재 포트폴리오에서는 앱의 배포 완성도보다 지도 기반 UX와 웹/앱 기능 정합성을 중심으로 설명하는 것이 적절합니다.

## 13. 한계와 개선점

| 한계 | 개선 방향 |
| --- | --- |
| React 웹의 상태가 `App.tsx`에 일부 집중되어 있음 | 패널별 route 또는 상태 store 도입을 검토합니다. |
| 지도/스트리밍 플로우에 대한 자동화 테스트가 부족함 | Playwright 기반 검색, 상세 분석, 북마크 회귀 테스트를 추가합니다. |
| Flutter와 웹의 UI 컴포넌트가 완전히 같은 토큰 빌드 파이프라인으로 묶여 있지는 않음 | design token 변환 자동화를 추가합니다. |
| 리뷰 광고성 판단 근거 설명이 부족함 | 키워드 하이라이트, 판단 근거 문장, 사용자 피드백 반영 UI를 추가합니다. |
| 모바일 웹 최적화 검증이 제한적임 | 실제 기기 기준 지도/패널 전환 UX를 추가 점검합니다. |

## 14. 프론트엔드 역량 어필 포인트

- 지도 기반 탐색과 리뷰 분석이라는 비동기 흐름을 하나의 제품 경험으로 연결했습니다.
- SSE 스트리밍, 캐시 조회, 요청 취소, 중복 병합 등 실제 사용 중 발생하는 상태 꼬임을 처리했습니다.
- React 웹과 Flutter 앱의 기능 정합성을 맞추며 크로스 플랫폼 UI 구조를 설계했습니다.
- 디자인 토큰과 공통 컴포넌트를 정리해 화면 일관성을 유지했습니다.
- 빈 상태, 오류 상태, 로딩 상태, 사용량 부족 상태를 분리해 사용자가 현재 상황을 이해할 수 있게 했습니다.
